# Changelog

All notable changes to this project are documented in this file, following [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
Versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html) and are released as git tags `vX.Y.Z`.

## [Unreleased]

### Fixed

- `GET /api/feed/:feedId/membership` returns `clubId` for members only (null for outsiders); the public feed page uses it instead of guessing the club by name.

### Added

- Multi-factor authentication (MFA): users can add an authenticator app and passkeys as an additional factor at password sign-in, get backup codes (shown once), and turn MFA on or off in the new profile section "Multi-Faktor-Authentifizierung (MFA)". A password sign-in with MFA on returns `mfaRequired` and a short-lived `mfaToken` (new routes `/api/auth/mfa/*`); a backup code ends MFA and all other sessions. Operators can reset a locked-out user with `php bin/console app:user:disable-mfa <id|email>`.
- Notice e-mails for security events (password changed, MFA turned on or off, backup codes regenerated or used, passkey deleted, repeated failed sign-ins) with time, IP address, approximate location and browser.
- Security log of sign-ins and account-security events (not viewable in the app yet; kept for one year, cleaned by the new command `app:prune-security-events`, to be run by cron).
- Optional offline location lookup for these notices: MaxMind GeoLite2 City (`MAXMIND_ACCOUNT_ID`, `MAXMIND_LICENSE_KEY`, `GEOIP_DB_PATH`, database refreshed by `app:geoip:update`) or, without a key, the visitor's country from a header of a trusted proxy (`CLIENT_COUNTRY_HEADER`, default empty = off).
- Admin UI for feed self-join: club setting "Beitritt über Feeds" (off / internal feeds / also public feeds) on the club's general tab; private feeds get a section "Zugewiesene Mitglieder" (paginated list with search and source filter, add by member search or pasted e-mail list, remove single or selected); rotating a private feed's secret can withdraw the access of members who joined it themselves; the feed list shows the assigned count.
- Public feed page and accounts: a slim bar "Angemeldet als ..." (to the account, sign out) above all public pages for signed-in visitors; the subscribe split button gets "Zu meinem Konto hinzufügen" / "In meinem Konto anzeigen" depending on membership and subscription; new confirmation page `/feed/:feedId/join` (becomes a club member and adds the feed); the sign-in and signup flow passes the feed proof (identify, register, SSO start) so registration works under `RESTRICT_REGISTRATION`.
- "Mein Verein" tabs: the calendar shows the events of the personal subscription (month / list, audience filter preselected from the subscription, event dialog); the subscription tab chooses feeds and audiences and shows the personal calendar link with the usual subscribe button. The profile has a new section "Mein Kalender-Abo" to renew the personal link per club.
- App shell follows the club role: a plain `member` sees only the new page "Mein Verein" (`/clubs/:id/me`, tabs Calendar and Subscription, leaving the club) and never triggers calendar or settings requests; staff get "Mein Verein" in the navigation. Frontend API layer for the personal subscription and feed claim.
- Personal club subscription (backend): every club member (also plain `member` and admins) has one personal subscription per club with a selection of feeds and target groups behind a personal secret. New routes `GET|PUT /api/clubs/:id/my-subscription`, `POST …/my-subscription/rotate-secret` and `GET /api/clubs/:id/my-feeds`; claiming a feed adds it to the subscription; leaving or being removed from a club deletes it.
- Personal subscription served (backend): the ICS address `GET /api/feed/me/:id/ics?secret=…` (events of the selected feeds the member may currently access, with ETag/304) and the calendar view `GET /api/clubs/:id/my-events`.
- With `RESTRICT_REGISTRATION=true`, a feed address also allows creating an account when the feed's club lets new members in through that feed (club setting `feedSignup`; PRIVATE feeds need the secret): optional `feedProof` on `POST /api/auth/identify` and `/register`, `feed_id`/`secret` on the SSO start. It does not join the club by itself.
- New club role `member` (below `viewer`): belongs to the club but has no access to its content. Authorization is deny-by-default (only the own memberships, the minimal club record and leaving the club are open to a member; MCP tools reject members). Invitations and role changes accept `member`. New quota `staffPerClub` (500 viewers/editors/admins per club); `membersPerClub` is now 5000.
- `RESTRICT_CLUB_CREATION` (default false): when true, `POST /api/clubs` answers 403 `club_creation_restricted`. With `RESTRICT_REGISTRATION=true` as well, the first user may create the first club (bootstrap); afterwards clubs are created by the operator with the new command `php bin/console app:club:create` (`--name`, `--admin`, `--timezone`). `GET /api/auth/registration` returns `clubCreationAllowed`; the app hides club creation when it is not allowed and tells users without a club that they need an invitation. Invitations and MCP are unaffected. See the admin guide ("Security", "Operations", configuration reference).

- Club members: `GET /api/clubs/:id/members` is paginated and searchable on the server (`page`, `perPage` 1..100 default 10, `q` on name and e-mail, `role`; ordered by name then id; total in `X-Total-Count`, now also exposed by CORS; migration adds index `club_user(club_id, role)`). The members tab of "Manage club" uses it with search, role filter and paging and never loads the whole list.

- Club self-join through feeds: new club setting `feedSignup` (`off` | `internal` default | `public`, admin-editable via `PATCH /api/clubs/:id`, in club responses for staff) decides whether a signed-in non-member who opens a feed becomes a `member` through it (`internal`: `CLUB` and `PRIVATE` feeds, `public`: `PUBLIC` feeds too). New `POST /api/feed/:feedId/claim` (JWT, confirmed address, `{secret?}`; 404 `feed_not_found` for every lookup failure, 403 `member_signup_disabled`) and `GET /api/feed/:feedId/membership`. New table `feed_member` (access of members to `PRIVATE` feeds, `assigned` by staff or `claimed` by secret) with editor/admin endpoints `GET|POST /api/clubs/:id/feeds/:feedId/members`, `…/members/by-email`, `…/members/bulk-delete`, `DELETE …/members/:userId`; feed responses carry `assignedCount`; `POST …/regenerate-secret` accepts `{revokeClaimed}`; leaving or removal from the club deletes the feed access. Quota `feedMembersPerFeed` (5000); rate limit 20 per user and hour. Migration adds `club.feed_signup` (existing clubs: `internal`) and `feed_member`.
- Sign-in offers passkeys through the browser's and the password manager's autofill on the e-mail field (conditional UI); users without a passkey see no extra UI.

### Changed

- Deleting a passkey now needs a confirmation (password, or a mailed code for accounts without a password); `POST /api/auth/webauthn/register/verify` returns the id of the new passkey. The last passkey cannot be deleted while it is the only MFA factor.
- The password-changed mail now also names IP address, approximate location and browser.
- Backup codes are stored with a salted slow hash.
- The silent passkey autofill on the sign-in page no longer shows an error when it is dismissed or fails.
- Browsers in notices are recognised by a maintained parser (uap-php); in the Docker image its data is refreshed at build time.
- Small UI fixes: audience and location lists and the audience chips and filters are sorted alphabetically; the feed visibility "CLUB" is now called "Vereinsintern" and private feed assignment is described; the template picker loads templates in chunks of 5; "Import" is removed from the sidebar navigation; the dropdown arrow of selects no longer overlaps the text; the sign-in flow shows no required marker; the e-mail confirmation code is shown grouped as 123-456.
- Calendar search is the same everywhere: an autocomplete with at most 10 previews and a last entry "Alle Ergebnisse anzeigen" that opens the list with the search term. In the event calendar the list is the event list; on the public feed page and in "Mein Verein" the click opens the event dialog and the list shows the matches of all dates.
- Sign-in is kept across tabs and browser restarts: the refresh token is stored in the browser, the access token only per tab. Signing out applies to all open tabs of the browser.
- Sign-in and signup forms are marked up for password managers: a hidden username field and `current-password` / `new-password` autocomplete, so they are recognised as a login.

### Security

- MFA verification at sign-in is atomic: the guess budget per login token is exact (kept in the database), a lost race no longer burns a code, and stale state cannot be reused. The per-user and per-IP verify limits are best effort under parallel requests.
- Feed shared secrets and personal subscription secrets are now encrypted in the database (XChaCha20-Poly1305 with a key derived from `APP_SECRET`, bound to the column; format `enc:v1:<keyId>:<data>`); the API and the app still show the plaintext address. Existing plaintext values stay readable and are encrypted by the new command `php bin/console app:secrets:rotate` (the Docker entrypoint runs it at start, non-fatal). The same command re-encrypts everything after an `APP_SECRET` change: set `APP_SECRET_PREVIOUS` (old values, comma-separated) while rotating. `APP_SECRET` is now part of what a database backup needs to be readable. Migration widens `member_subscription.secret` to 255; `ext-sodium` is now a declared requirement.
- SSO (Google, Microsoft, Apple; sign-in and account linking): every flow now sends an OIDC `nonce`, kept in the signed `state`, and the ID token must carry exactly that nonce, so an ID token issued for another flow is refused (`oauth_failed`).
- SSO (Google, Microsoft, Apple): the signature of the ID token is now verified against the provider's JWKS (RS256 only; keys cached for 1 hour, at most one refetch per minute on an unknown key id). A failed fetch or invalid signature ends the sign-in with `oauth_failed`. The backend must reach `www.googleapis.com`, `login.microsoftonline.com` and `appleid.apple.com` over HTTPS. `lcobucci/jwt` is now a direct dependency.
- SSO (Microsoft): the immutable tenant and object id (`tid`/`oid`) of the verified ID token are stored on the linked account (migration adds `oauth_account.tenant_id`/`object_id`, backfilled at the next sign-in) and used as fallback key, so a changed per-app `sub` still finds the account; differing stored ids fail closed (`oauth_failed`).

### Changed

- Security (audit L10): the Mapbox token (`access_token`, which Mapbox accepts only as a query parameter) no longer reaches the logs. `RedactTokensProcessor` also masks `access_token` values (query string and JSON form) and replaces exceptions whose message or trace carries a secret by a redacted array; `MapboxMapImageProvider` throws a `MapImageUnavailableException` with only the HTTP status or "transport error" (no URL, no previous), and `/api/map/image/*` answers 502 (`no-store`) instead of a generic 500 when Mapbox fails.
- Security: Symfony components updated from 8.1.0/8.1.9 to 8.1.11 (`composer audit` reported 18 advisories in 11 packages, now none), among them the `HEAD` handling of `access_control` rules with `methods: [GET]`, path-info handling of a script-name-prefixed path, trusted-proxy `private_ranges`, and serializer/http-client/security-http fixes. No configuration change needed; `symfony/flex` and `symfony/monolog-bundle` minimum versions rose to `^2.12` and `^4.1` in `composer.json`.
- Security (audit I2): directory URLs such as `/assets/` are never listed. With `mod_rewrite` they fall through to the SPA (as before, now documented and tested); without it `.htaccess` answers 403 for directory URLs. No `Options` line is added (it would be a 500 under a restrictive `AllowOverride`). `*.map` files are denied in `.htaccess` and `docker/Caddyfile`, and the Vite build sets `sourcemap: false` explicitly (none are emitted).
- Security (audit L9): fetching a holiday calendar from an ICS URL follows at most 3 redirects (every target is checked against private networks), runs before the database write instead of inside a transaction (a failed fetch leaves the stored holidays untouched) and is limited to 20 fetches per user and hour (create by URL and refresh, 429 `rate_limited` + `Retry-After`). The automatic refresh and `app:holidays:refresh` are not throttled.
- Security (MCP): an authorization request is now bound to the browser that started it. `GET /api/oauth/authorize` sets an HttpOnly, SameSite=Lax cookie `oauth_consent_<requestId>` (path `/api/oauth`, 10 minutes) and stores only its hash; the consent page API (`GET /api/oauth/authorization-request/{id}`, `POST /api/oauth/authorize/decision`) answers 404 `authorization_request_not_found` without the matching cookie, so a signed-in user who learns a request id cannot approve it. The consent link must be opened in the browser that started the connection; requests pending during the update must be restarted. A frontend on another origin must be on the same site as the API (see the admin guide, `docs/admin/docs/security.md`).
- MCP (breaking for some deployments): an empty `MCP_ALLOWED_CLIENTS` no longer allows every client, it now allows none; all clients need the explicit value `*` (only alone: `*` combined with other entries or unknown entries fails at boot). Deployments that relied on the empty value must set `MCP_ALLOWED_CLIENTS=*`. Clients registered earlier without a known family are re-checked against the current setting at authorization and are refused without `*`; existing grants and tokens keep working until disconnected.
- MCP consent page and "Connected apps": the app is identified by a label the server derives from the matched client family (Claude, ChatGPT, Gemini), never by the self-declared name, which is shown only as "calls itself ..." and only when it differs. Local (loopback) and custom ChatGPT connector callbacks get an extra warning. API: `clientName` is replaced by `label`, `claimedName` (and `redirectHost` in the grants list, `callbackRisk` in the authorization request).
- Security (audit API-52): Mapbox spending paths have per-user and per-IP limits (per hour: map tiles 1800 per user and 3600 per IP, styles and fonts 900 per user plus 60000 per day for the instance, anonymous static map images 360 per IP), answered with 429 `rate_limited` and `Retry-After`. Behind a reverse proxy `SYMFONY_TRUSTED_PROXIES` must be set, otherwise all clients share the IP limits.
- MCP: the client family `grok` is removed (its redirect URI is unknown, so it accepted nothing); the default `MCP_ALLOWED_CLIENTS` is now `claude,openai,gemini`. An existing deployment that sets `MCP_ALLOWED_CLIENTS` with `grok` must remove it, otherwise the application fails at boot.
- Security (audit L13): the SSO login code is now bound to the browser tab that started the sign-in (PKCE S256), so a callback link produced in someone else's flow cannot sign a victim into the attacker's account. `GET /api/auth/oauth/{provider}` requires `code_challenge`; `POST /api/auth/token` (`one_time_token`) requires `code_verifier` (400 `invalid_code_verifier`). Opening the callback link in another tab or browser shows a message to start the sign-in again.
- Security (audit L7): adding a passkey now requires proof of the account holder: the password, or for accounts without one a 6-digit code mailed to the address (own purpose, a deletion code is not valid). `GET /api/auth/webauthn/register/options` became `POST` with `{password}` or `{code}`; new `POST /api/auth/webauthn/register/code`.
- Help pages show a small note above the footer links that the help texts were created with the help of AI.
- Address search (geocoding suggestions) uses the standard Mapbox geocoder again and finds street addresses only; places (POIs) are no longer suggested and the `name` field is removed from `GET /api/map/geocode/suggest`.
- ICS export (feed, member download, single event): `LOCATION` and the Apple map address are now one part per line, "name, street, ZIP city, country" (empty parts skipped), like Apple Calendar's own export, so Apple Calendar shows the map.
- Public feed page: the single-event calendar download ("Add to calendar") is now generated by the backend (`GET /api/feed/{feedId}/events/{eventId}/ics`) and is identical to the subscription (title with extras, emoji legend, `GEO`, `X-APPLE-STRUCTURED-LOCATION` for Apple Calendar maps, `VTIMEZONE`).
- ICS export (feed and member download): the event title is now `emoji title (extras)`, and the description additionally explains the emojis used (`emoji badge name`).
- Sign-in page: the Google, Microsoft and Apple buttons now follow the providers' brand guidelines (official logos, fixed brand colors with light and dark variants, fixed wording).

### Fixed

- Apple sign-in: the authorize request now sends `response_mode=form_post`, which Apple requires for the name and email scopes.

### Added

- Admin guide for operators (English) in `docs/admin/`, published on GitHub Pages at https://silviokennecke.github.io/club-calendar/: quick start with Docker Compose, hosting without Docker (Apache, nginx), configuration reference, SSO, mail and maps, security and legal documents. Ready-to-download Docker Compose and `.env` examples are in `docs/admin/docs/examples/`. The operator content of `docs/ops/OPERATIONS.md` moved there; the file now only holds maintainer notes.
- PDF export: the document metadata now carry the club name as author and the app (with its address) as creator.
- Holiday calendars have a type (public holidays, school holidays, other) and can be imported as predefined calendars from OpenHolidays (country preselected Germany, optional state, kinds public/school holidays); the data is stored in the database, refreshed automatically when older than 3 months and manually on demand. New console command `app:holidays:refresh`; the server must reach `openholidaysapi.org`.
- Event series: choose which holiday calendars apply to "skip holidays" (default all), on create and when changing the series.
- PDF export: optional "Show holidays" selection of holiday calendars (default none); public holidays are coloured with their name, school holidays coloured with the name on the first day only.
- PDF export of a calendar (`GET /api/calendars/{id}/events.pdf`): month grid, quarter overview, annual overview and agenda, A4/A3, portrait/landscape, with a legend for property icons; output language and first weekday follow the profile. At most 366 days and 2000 events per PDF. Requires the PHP extensions `gd` and `intl`.
- User documentation for all features in `/help`, including the subscribe guide with app tabs (iPhone/iPad, Mac, Outlook, Google Calendar) at `/help/publishing/subscribe`; the old `/help/subscribe` URL (with `?app=`) redirects there.
- In-app help at `/help` (German and English) with full-text search and contextual `HelpLink`s, compiled from Markdown at build time; screenshots are generated with Playwright (`npm run docs:screenshots`).

### Changed

- PDF quarter overview is now a day list (one column per month, one row per day, one line per event with time, icons, name and features, weekends tinted) with a per-page icon legend instead of three small month grids.
- E-mail confirmation now needs a signed-in, restricted session: registration, password login, refresh and SSO of an unconfirmed account return tokens (`emailVerificationRequired`), but every route except the own profile, consent, sign-out and the confirmation itself answers `403 email_verification_required`. `POST /api/auth/verify-email` takes only `{code}` with that session and returns a fresh token pair; `POST /api/auth/resend-verification` needs the session and no body. Login of an unconfirmed account no longer answers `403 email_not_verified`, the SSO callback no longer redirects with `error=email_verification_required`, and the `loginToken` / `EMAIL_VERIFICATION_LOGIN_TOKEN_TTL` are gone.
- Page footers show a single help link: the help center (`/help`), on public calendar pages the subscribe guide; the help pages show only the legal links.

### Security

- Content-Security-Policy: `style-src` no longer allows `'unsafe-inline'`; only own files and the hash of emoji-mart's fixed stylesheet. Custom web server configs (nginx) must take the new header from the admin guide (`docs/admin/docs/hosting-without-docker.md`).
- Pre-hijacking of accounts is closed: someone who registers a stranger's address with an own password can no longer be confirmed by the mailbox owner's code. Only the session that proved the password (or SSO login) and holds the mailed code can confirm the address.
