## HIGH

### H2 — Pre-account hijacking: attacker's password survives e-mail verification  [AUTH-1]

> **Status (git-log check 2026-10-15): PARTIALLY FIXED** — password reset added in `223a8d1`/`e55e266` (hashed single-use token, ends all sessions, confirms the address), so the victim can recover. At HEAD verification still keeps the attacker's password (`EmailVerificationService::revokeUnprovenSsoAccess` only) and registration is not pending-until-verified. **Still open: the core takeover path.**
- **Attack scope:** unauthenticated remote; needs a click on the genuine mail, or a mail link scanner issuing the GET
- **Description:** `POST /auth/register` stores an attacker-chosen password for any address and mails a link to the owner. `GET /auth/verify-email` marks the address verified but deliberately keeps the password (`revokeUnprovenSsoAccess`). Attacker then logs in as the verified victim. No password reset exists, so the victim cannot recover; later Google SSO links to the already-verified account without revoking anything. Attacker sees all clubs, calendars and private feed secrets. Also grants access when an admin adds the victim via `addMember`.
- **Affected:** `EmailVerificationService.php:52-101`, `AuthController.php:50-120`, `AuthService.php:28-44,192-201`
- **Fix (one of):** clear password on verification and make the owner set one via the mail token; keep registrations pending until verified (re-registration overwrites); make verification a POST from a frontend page (defeats scanners). Add password reset; bump `tokenVersion` on verification.
- **Notes:** CWE-287/640. Confidence high (behaviour is intentional per code comment).

## INFO / hardening

- **I2 `.htaccess`**: `Options -Indexes -MultiViews` is intentionally not set (breaks managed hosting with restrictive AllowOverride); keep sourcemaps off (frontend agent saw none in the build). [BACKEND-F13]
- **I3 Misc backend**: fixtures password `password123` (dev only); `PruneUnverifiedUsersCommand` not scheduled; refresh token is hand-rolled HS256 JWT with standard base64 rather than base64url; `OidcProvider::parseIdToken` doesn't validate signature/iss/aud/nonce (OK: token from token endpoint over TLS) and no PKCE; local `config/jwt/public.pem` is 0666; 404-vs-403 existence oracle on IDs (UUIDv7, not guessable); `lastClubId/lastCalendarId` unvalidated in `PATCH /me`. [BACKEND-F14, AUTH-Info, AUTHZ-F8/F9]
- **I4 Frontend**: route guards client-side only (backend enforces); IDs placed into API paths without `encodeURIComponent` (`useCalendarData.ts:48`, `api.ts:178`); OAuth provider id into href unencoded; legacy `accessToken` storage key still read. [FRONTEND-F7/F9, F4]
- **I5 Dependencies**: CI runs no `npm audit --omit=dev` (and no `composer audit`); dev tooling lags (`vitest`/`tinypool` critical advisories, fix = vitest 5.0.3, a major bump). Dev-only, not in the production bundle. [FRONTEND-F5]
