# Frontend Internationalization (i18n) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add English/German language support to the frontend SPA with browser-language detection, localStorage persistence, and a language switcher for both logged-in users and anonymous feed viewers.

**Architecture:** Use `i18next` + `react-i18next` (industry standard, synchronous bundle-included resources) with `i18next-browser-languagedetector` for automatic browser language detection. Language preference stored in `localStorage` key `language` for all users (no backend change required). A `LanguageSwitcher` component renders in the ProfilePage Localization section (logged-in) and in the FeedPage header (anonymous).

**Tech Stack:** `i18next@24`, `react-i18next@15`, `i18next-browser-languagedetector@8` — all bundled with the existing Vite build, no lazy loading of translation files.

## Global Constraints

- Frontend only — no backend code, no entity changes, no API changes.
- Supported languages exactly: `en` (English, fallback) and `de` (German).
- Language stored in `localStorage` key `'language'` for all users (both authenticated and anonymous).
- Browser language auto-detected via `navigator.language` if no localStorage value exists.
- All `t()` key paths must exist in both `en.json` and `de.json` — the parity Vitest test in Task 2 enforces this.
- FullCalendar locale must also switch dynamically (both `CalendarPage` and `FeedPage` currently hardcode `locale="de"`).
- **Refactor awareness:** A separate shared-UI-components refactor (`docs/superpowers/plans/2026-06-27-shared-ui-components.md`) touches many of the same pages. If that refactor has already been applied when you work on Tasks 3–9, check the current file state — component structure may differ but the string-wrapping task (find hardcoded UI strings → replace with `t()`) remains the same.

import { describe, it, expect } from 'vitest'
import en from '../../locales/en.json'
import de from '../../locales/de.json'

function collectKeys(obj: unknown, prefix = ''): string[] {
  if (obj === null || typeof obj !== 'object') return [prefix]
  if (Array.isArray(obj)) return [prefix]
  return Object.entries(obj as Record<string, unknown>).flatMap(([k, v]) =>
    collectKeys(v, prefix ? `${prefix}.${k}` : k)
  )
}

describe('locale files', () => {
  it('en and de have identical keys', () => {
    const enKeys = collectKeys(en).sort()
    const deKeys = collectKeys(de).sort()
    const missingInDe = enKeys.filter(k => !deKeys.includes(k))
    const extraInDe = deKeys.filter(k => !enKeys.includes(k))
    expect(missingInDe, 'Keys in en but not in de').toEqual([])
    expect(extraInDe, 'Keys in de but not in en').toEqual([])
  })
})

### Task 10: GitHub Actions CI job for translation key parity

**Files:**
- Modify: `.github/workflows/ci.yml`

**Interfaces:**
- Consumes: `frontend/src/lib/__tests__/i18n.test.ts` (Task 2) — the parity Vitest test that CI will execute
- No new npm packages needed

**Approach:** i18next has no dedicated CLI parity checker (unlike phpunuhi for PHP). The idiomatic JavaScript equivalent is a Vitest test that compares the key sets of both JSON files — exactly what Task 2 defines. The CI job simply runs that test in isolation. It is a dedicated job with no service dependencies (no MySQL, no backend, no Playwright), so it completes in ~30 seconds and blocks PRs immediately when a locale key is missing.

The job is added to the existing `.github/workflows/ci.yml` alongside the `backend` and `frontend` jobs, making the i18n check a first-class gate on every PR and push to main.

- [ ] **Step 1: Read the current `.github/workflows/ci.yml`**

Read the file before editing:
```bash
cat .github/workflows/ci.yml
```

- [ ] **Step 2: Add the `i18n-check` job to `.github/workflows/ci.yml`**

Add the following job block after the existing `backend` job definition (before the `frontend` job). It runs independently — no `needs:` — so it runs in parallel with `backend` and doesn't block the E2E job:

```yaml
  i18n-check:
    name: i18n — translation key parity (en ↔ de)
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version-file: .nvmrc
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Check en ↔ de key parity
        working-directory: frontend
        run: npx vitest run src/lib/__tests__/i18n.test.ts --reporter=verbose
```
