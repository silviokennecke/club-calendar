# Club Calendar

A web app for clubs to manage and publish event calendars.

## Stack

- **Runtime (backend):** PHP 8.4
- **Backend:** Symfony 8.1 (attribute routing, autowiring)
- **ORM:** Doctrine ORM (attribute mapping, UnderscoreNamingStrategy)
- **DB migrations:** `doctrine/migrations`
- **JWT:** `lexik/jwt-authentication-bundle` (RSA keys)
- **OAuth SSO:** `knpuniversity/oauth2-client-bundle` + league providers
- **WebAuthn:** `web-auth/webauthn-lib`
- **ICS generation:** `eluceo/ical`
- **PDF export:** `dompdf/dompdf` (needs `ext-gd`, `ext-intl`; the Docker image installs both)
- **Validation:** `symfony/validator` (DTO constraints)
- **Tests:** PHPUnit 11 + `symfony/test-pack`
- **Runtime (frontend):** Node.js v22, TypeScript
- **Frontend:** Vite SPA + React 19 + React Router v7 (data router, routed modals), TanStack Query, Tailwind CSS v4
  with the redesign's design tokens (`src/index.css`), shared building blocks on a minimal shadcn/Base UI basis,
  i18next (de/en), light/dark/system theme; own month/week calendar views (no FullCalendar); Mapbox GL and emoji-mart
  loaded lazily; route-level code splitting (`src/pages/lazy.ts`)
- **MCP:** `symfony/mcp-bundle` (pinned `~0.15.0`, pre-1.0; mcp/sdk 0.9) + a hand-written OAuth 2.1 authorization server (see "MCP server and OAuth")
- **Frontend tests:** Vitest + Testing Library, Playwright (E2E)
- **Database:** MySQL 8 or MariaDB (no `server_version` in `doctrine.yaml`: DBAL detects the platform; a fixed `8.0` broke MariaDB introspection)

## Monorepo Structure

- `backend/` — Symfony API server (port 3001); also serves the built SPA from `backend/public/`; module and
  infrastructure reference in `backend/AGENTS.md`
- `frontend/` — Vite/React single-page app (dev server port 5173, `npm run dev:frontend`); conventions in
  `frontend/AGENTS.md`
- `docs/ops/` — `E2E.md` (setup/run of the isolated Playwright environment), `OPERATIONS.md` (maintainer-only notes: migration history, drift tests; operator content lives in `docs/admin/`), `BACKLOG.md` (open backend gaps, open security risks, open operations and design items)
- `docs/admin/` — English admin guide for operators (Zensical site, published to GitHub Pages by `.github/workflows/docs.yml`), with the operator example files in `docs/admin/docs/examples/`; kept current by working rule 10
- `docs/api/openapi.yaml` — hand-written OpenAPI 3.1 reference of every `/api` route (schemas, error codes, auth,
  feed/robots rules, limits); not served by the app. `backend/tests/Unit/OpenApiSpecTest.php` fails when a route
  and the document drift apart: update it with every route change

## Configuration

Backend settings are environment variables (`backend/.env.example`, local overrides in `backend/.env.local`, gitignored). `APP_URL` is the public address of the app (SPA and API share one origin); `FRONTEND_URL`, `BACKEND_URL` and `WEBAUTHN_RP_ID` (host of `APP_URL`) default to it and only need to be set for split setups. Defaults live in `backend/config/services.yaml` (`env(...)` parameters). Host header (audit M2): links in mails, redirects and the OAuth `redirect_uri` are built only from these URLs (`RequestContextListener` pins the router's request context to `BACKEND_URL`), and `framework.trusted_hosts` accepts only the hosts of `APP_URL`/`FRONTEND_URL`/`BACKEND_URL`, the comma-separated extra hosts in optional `TRUSTED_HOSTS` (e.g. a `www` alias) and loopback (`localhost`, `127.0.0.1`, `[::1]`: container health check, dev, E2E); any other `Host` is a 400 (`App\Security\TrustedHostsEnvVarProcessor`). A production host reachable under another name must be listed in `TRUSTED_HOSTS`. Optional: `APP_SECRET_PREVIOUS` (old APP_SECRET values while rotating, see "Secrets at rest"), `MAPBOX_TOKEN`, `GOOGLE_*`, `MICROSOFT_*`, `APPLE_*` (SSO), `WEBAUTHN_USER_VERIFICATION`, `FEED_ICS_*` (public feed ICS window/cap, see "ICS Feed Endpoint"), `RESTRICT_CLUB_CREATION` (bool, default false: when true, `POST /api/clubs` is refused with 403 `club_creation_restricted`; clubs are then created by the operator with `app:club:create`; bootstrap exception: with `RESTRICT_REGISTRATION=true` as well and no club existing yet the first user may create the first club; `GET /api/auth/registration` returns `clubCreationAllowed`; `App\Service\ClubCreationPolicy`; invitations and MCP unaffected), `RESTRICT_REGISTRATION` (bool, default false: when true, only e-mail addresses with an open club invitation may register; the CLI is the way to create the first user). In the `test` environment `TEST_DATABASE_URL` falls back to `DATABASE_URL` (`config/packages/doctrine.yaml`): the tests truncate all tables, so always point it at a separate test database.

## Working Rules

1. **Commit after every feature or fix** — create a git commit as soon as an implementation task is complete, before moving to the next task.
2. **Keep CLAUDE.md, backend/AGENTS.md and frontend/AGENTS.md up to date** — update these files whenever the stack, architecture, or module structure changes.
3. **Write tests** — add PHPUnit integration tests for every backend feature (`tests/Controller/*.php`). E2E tests use Playwright (`frontend/e2e/`).
4. **Always use UUIDs for entity IDs** — never use auto-increment integers. Use `Uuid::v7()->toRfc4122()` assigned in the constructor, with `#[ORM\Column(length: 36)]` (no `#[ORM\GeneratedValue]`). The `getId()` return type must be `string`, not `?int`.
5. **Use shared UI components** — Before adding structural JSX or Tailwind layout patterns to a frontend page, check `frontend/src/components/ui/shared/` (exports in `index.ts`, table in `frontend/AGENTS.md`), e.g. `Button`/`LinkButton`/`IconButton`, `SplitButton`, `Field` + `TextInput`/`TextArea`/`NativeSelect`, `PasswordField`, `Toggle`, `Tag`, `StatusBadge`, `Banner`, `toast`, `EmptyState`, `ConfirmDialog`, `FormDialog`, `Modal`/`ModalFrame`/`DialogFrame`, `CopyField`, `Chip`/`ChipSelect`, `FilterPillGroup`, `SearchInput`, `Pagination`, `AutocompleteInput`, `EmojiPicker`, `Stepper`, `LangSwitch`, `ThemeSwitch`, `Skeleton`, `FullPageLoader`, `ErrorSummary`, `UnsavedChangesDialog`, `Logo`, `Icon`. Import from `@/components/ui/shared`. For Mapbox maps, use `useMapbox` from `frontend/src/components/locations/useMapbox.ts` instead of duplicating the initialization boilerplate.
6. **Texts via i18n** — every UI text is a key in `frontend/src/locales/de.json` and `en.json` (identical keys and placeholders, enforced by `src/lib/__tests__/i18n.test.ts`); remove keys that are no longer used.
7. **Orchestrate, don't implement** — you are the orchestrator/manager. All work is done by subagents (Haiku or Sonnet; ask before using Opus). Pick the most efficient model for every task. Every subagent gets exactly one specific task, to keep its context small.
8. **Unsigned commits as fallback** — if committing fails due to signing issues, commit without signing the commit.
9. **Help pages** — a new or changed user-visible feature gets or adjusts a help page in `frontend/docs/de` and `en` (see "End-user documentation (/help)"). On every feature change, check whether the end-user documentation (`frontend/docs/de` and `en`, incl. screenshots) is affected and update it automatically, without asking first; the final summary to the user must explicitly list which help pages were updated. Help pages are for non-technical users: plain, short, task-oriented language; no feature advertising and no technical background (protocols, libraries, security internals) unless the user must act on it; explain a cross-cutting topic once on its natural page and link to it instead of repeating it.
10. **Admin guide** — every change that affects installation or operation updates `docs/admin/` (and its example files in `docs/admin/docs/examples/`) automatically, without asking first: environment variables (new, renamed, removed, changed defaults), config files, protection mechanisms (rate limits, sign-in, SSO, security headers), cron jobs, console commands, Docker image and entrypoint, upgrade steps, legal documents and consent handling. Write for operators: plain English, task-oriented, no code internals (class or file names). The strict build (`zensical build` in `docs/admin/`) must pass. The root `docker-compose.yml` stays the developer setup; the admin examples are the operator setup. The final summary must list which admin pages were updated.

## Docker

`docker/` holds everything for the container image (`Dockerfile`, `Caddyfile`, `php-fpm.conf`, `php.ini`, `entrypoint.sh`, `Dockerfile.dockerignore`). Build from the repo root: `docker build -f docker/Dockerfile -t club-calendar .`. Multi-stage (composer, Node/Vite, Caddy) into `php:8.4-fpm-alpine`: Caddy serves the SPA and proxies `/api/*` to PHP-FPM on one origin, running as `www-data` on port 8080. The SPA is built with an empty `VITE_API_URL`, which `frontend/src/lib/apiUrl.ts` resolves to `window.location.origin`, so the image is domain-independent. The entrypoint also generates JWT keys if missing (mount a volume at `config/jwt`) and runs migrations (`RUN_MIGRATIONS=0` disables). Required env vars are listed at the top of `entrypoint.sh`. `.github/workflows/docker.yml` builds `ghcr.io/<owner>/<repo>` on push to main (tag `main`) and on PRs to main (tag `pr-<number>`, pushed only for PRs from the same repo). Releases are driven by `.github/workflows/release.yml` (workflow `permissions` default to `contents: read`; `contents: write` only on the autofix and release jobs, `packages: write` only on the image job: a caller must grant what a called job declares) on tags matching `v[0-9]+.[0-9]+(.[0-9]+(-(beta|rc).[0-9]+)?)?`: validate tag → CI (`ci.yml`, reusable; runs `composer audit` and `npm audit --omit=dev` in the backend job) → image (`docker.yml`, reusable; tags: version without `v`; `latest` only for stable tags, not `-beta`/`-rc`) → GitHub Release (notes from the matching `## [X.Y.Z]` section of `CHANGELOG.md` if non-empty; `-beta`/`-rc` marked as prerelease). Keep `CHANGELOG.md` (Keep a Changelog format, `## [Unreleased]`) up to date with user-visible changes; rename Unreleased to the version when tagging.

## Deployment

There is no deploy tooling in the repo any more (Deployer was removed in b51cc47; no `deploy` scripts in `package.json`). Build with `npm run build` (Vite outputs into `backend/public/`, see `frontend/vite.config.ts`) or use the Docker image, and run composer install, migrations and cache clear/warmup on the target (keep `.env.local` and `config/jwt/` outside the release). Settings are documented in `.env.example`; the docroot is `backend/public`. `backend/public/.htaccess` routes `/api/*` to Symfony and everything else to the SPA's `index.html`. Both the `.htaccess` and `docker/Caddyfile` send `Referrer-Policy: no-referrer` for `/feed/*` and `/api/feed/*` (other web servers, e.g. nginx: add the same header, see `docs/admin/docs/hosting-without-docker.md`); `X-Robots-Tag: noindex` for the feed API comes from `FeedResponseHeadersListener` in the backend, not from the web server.

Security headers (audit M4) live in both `backend/public/.htaccess` and `docker/Caddyfile` and must stay identical (`backend/tests/Unit/SecurityHeadersConfigTest.php`): `Content-Security-Policy` (`default-src 'self'; script-src 'self'; style-src 'self' 'sha256-+A14ONesVdzkn6nr37Osn+rUqNz4oFGZFDbLXrlae04='` (no `'unsafe-inline'`: React sets `style=` through the CSSOM, which CSP does not block; sonner's CSS ships as a file because `frontend/vite/sonner-css.ts` removes its `<style>` injection; the only allowed inline stylesheet is emoji-mart's fixed one in its shadow DOM, by hash, guarded by `frontend/src/lib/__tests__/cspStyleHash.test.ts`); `img-src 'self' data: blob:`; `connect-src 'self'`; `worker-src 'self' blob:`; `frame-ancestors 'none'`; `object-src 'none'`, ...), `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Permissions-Policy`, `Cross-Origin-Opener-Policy: same-origin` (the OAuth flow is a full-page redirect, no popups) and a default `Referrer-Policy: strict-origin-when-cross-origin` (feeds keep `no-referrer`). There are no third-party hosts: Mapbox goes through `/api/mapbox` (tiles/styles/fonts: signed-in users only, 401 `missing_token` otherwise; anonymous pages use the public static images `/api/map/image/*`), emoji-mart data is bundled, fonts are self-hosted. CSP rules for contributors: no inline `<script>`, no `eval`, no `<style>` element and no `setAttribute('style', ...)`/`style="..."` in HTML strings (React `style={{}}` and `el.style.x = ...` are fine); `frontend/e2e/csp.spec.ts` (`E2E_CSP=1`, production build, see `docs/ops/E2E.md`) fails on any `securitypolicyviolation` (the theme bootstrap is `frontend/public/theme-init.js`); a new third-party host must be added to the policy in BOTH files and the test; split setups (`VITE_API_URL` on another origin) must add that origin to `connect-src` and `img-src` (static map images; `e2e/csp.spec.ts` injects both). HSTS is set by `.htaccess` only for HTTPS requests; Caddy runs behind a TLS terminator, which must send `Strict-Transport-Security` (see `docs/admin/docs/security.md`). `.htaccess` also denies `*.env`, `*.pem`, `*.log`, `*.map` (Caddy `@private` the same; `build.sourcemap: false` in `frontend/vite.config.ts`) and answers 403 for directory URLs when `mod_rewrite` is missing (with it they fall through to the SPA, so `/assets/` is never listed); deliberately no `Options -Indexes` line (a 500 under a restrictive `AllowOverride`).

## Domain Concepts

- **Club** — the top-level entity; has one or more Calendars; managed by its members (Users via `ClubUser` with role `member`/`viewer`/`editor`/`admin`, hierarchy member < viewer < editor < admin (`ClubRole`); `member` only belongs to the club and is NOT staff: authorization is deny-by-default (voters require viewer for `CLUB_MEMBER`/`CALENDAR_MEMBER`, so every club- or calendar-scoped route is 403 `forbidden` for a member), the explicit allow-list is `GET /api/auth/me`, `GET /api/clubs` and `GET /api/clubs/{id}` (minimal: id, name, timezone, role) and leaving (`DELETE …/members/{ownId}`, voter `CLUB_ANY_MEMBER`, the only attribute that admits a member; the service re-checks admin for removing others); `tests/Controller/MemberRoleTest.php` iterates all club/calendar routes and fails when a member gets anything but 403 outside the allow-list; MCP tools reject members (`list_clubs` hides their clubs); viewer reads; editor also writes events, series, templates, locations, properties, features, target groups, holiday calendars and reads feeds; admin also manages calendars, members, invitations and club settings); members join only by accepting an **Invitation** (no direct add); with `RESTRICT_CLUB_CREATION` only the operator creates clubs (`app:club:create`); a club never has zero members: the last member cannot be removed or leave (422 `last_member`, club row locked for the check), the last admin cannot be demoted/removed/leave while others remain (422 `last_admin`), and `DELETE /api/auth/me` is refused with 422 `last_admin_of_club` while the user is the last admin of a club (delete the club first or demote to a lower role)
- **ClubInvitation** — an invitation of an e-mail address to a club (see "Club invitations" below); pending, accepted or declined, valid 7 days, pending and expired ones stay listed and can be re-sent at any time (60 s cooldown per invitation)
- **Calendar** — belongs to a Club; contains Events, EventTemplates, Properties, Features, HolidayCalendars, and reference data per calendar; can be archived (read-only) or duplicated
- **CalendarFeed** — a publishable view of 1..n Calendars of a Club (ICS + web) with one of three states: `PUBLIC` (by link, search
  engines may index it), `CLUB` ("Vereinsintern", default: by link, never indexed)
  or `PRIVATE` (shared-secret protected); the web view merges published events and holiday events of all selected non-archived calendars; ICS lists events only, never holidays; scoped to a Club; see `docs/api/openapi.yaml`
- **Event** — a single occurrence on a Calendar; optional plain-text `note` (max 2000 chars, trimmed, empty = null; copied from the template; ICS `DESCRIPTION`, shown in the public feed); may be based on an EventTemplate; may belong to an EventSeries
- **EventSeries** — a recurrence rule (weekly, every two weeks, monthly on the n-th weekday; until a date or a count; skip holidays) with the events created from it; edit/delete "only this event" or "all events of the series" (`scope`); the rule can be changed later ("Reihe ändern", `PATCH …/event-series/{id}`: only future events change, past ones stay). ICS imports with RRULE create single events, not series
- **EventTemplate** — reusable event definition (name, time, location, properties, optional `note`)
- **Property** — a badge on events (e.g. "Schützentracht"); can have an emoji icon
- **Feature** — an extra (optional add-on) of events (e.g. "Bonusschießen")
- **TargetGroup** — an audience (group) of events (e.g. "Schüler", "Jugend", "Erwachsene"); scoped to a Club
- **Location** — a venue with an address and optional map position; scoped to a Club
- **HolidayCalendar** — a source of holidays/school breaks for a Calendar (`HolidayEvent`s) with a `type` (`public`|`school`|`other`) and a `source` (`ics` address or predefined `openholidays`, imported from openholidaysapi.org and stored in the DB, refreshed when older than 3 months or via `app:holidays:refresh`); shown in the calendar views, selectable for series "skip holidays" and the PDF export; the ICS fetch (`HolidayCalendarService`) runs BEFORE the short write transaction (a failed fetch keeps the stored holidays), follows at most 3 redirects (`MAX_REDIRECTS`; `NoPrivateNetworkHttpClient` re-checks every redirect target) and user-initiated fetches (create by URL, refresh) are limited to 20 per user and hour (`AuthRateLimiter::assertHolidayFetchAllowed`, 429 `rate_limited`; auto-refresh and the CLI are not throttled)
- **McpGrant** — a user's connection of an AI client (`OAuthClient`) to the MCP server, with scopes and `McpToken`s (see "MCP server and OAuth")
- **User** — e-mail addresses are stored trimmed and lower-cased everywhere (`App\Service\EmailAddress::normalize`, applied by the entity setters/constructors and every lookup); code compares them exactly and does not rely on column collations (the unicode_ci columns still equate look-alikes like "é"/"e", so lookups that matter re-check with `===`); signs in with password, Google/Microsoft SSO (`OAuthAccount`) or passkeys (`Passkey`); e-mail confirmation by 6-digit code (`EmailVerification`)

## Audit fields

All domain entities carry `updated_at` (NOT NULL) and `updated_by_id` (nullable FK to `user`, `ON DELETE SET NULL`, so account deletion keeps working) via `Entity\Trait\HasUpdateAudit` + `UpdateAudited`: `Club`, `ClubUser`, `ClubInvitation`, `Calendar`, `CalendarFeed`, `Event`, `EventSeries`, `EventTemplate`, `Property`, `Feature`, `TargetGroup`, `Location`, `HolidayCalendar`, `HolidayEvent`, `MemberSubscription`. `App\Doctrine\UpdateAuditListener` (prePersist + onFlush) fills them centrally; `updated_by` is the user of the token storage (JWT and MCP firewall), null for CLI, fixtures and tests without a request user. Adding or removing rows of association entities (`EventTargetGroup|Property|Feature`, `EventTemplate*`, `CalendarFeedCalendar|TargetGroup`, `MemberSubscriptionFeed|TargetGroup`) stamps the owning entity, so services need no explicit touch. Not audited: `User`, auth/token/nonce/log entities (`RefreshToken`, `EmailVerification`, `PasswordReset`, `EmailChange`, `Passkey`, `UserTotp`, `MfaBackupCode`, `SecurityEvent`, `OAuthAccount`, `AuthNonce`, `OAuth*`, `Mcp*`), `LegalDocument`, `UserConsent` and the join entities themselves. Not exposed in the API. A new domain entity: use the trait, implement the interface, add the migration columns. Raw SQL inserts must supply `updated_at`.

## Content version

`calendar.content_version` (varchar(36), UUIDv7, `Calendar::getContentVersion()`, not in the API) is an opaque token that changes with every change of a calendar's feed output (events and their assignments, series, properties, features, holidays, the calendar itself, club-scoped target groups/locations and the club time zone); consumed by the ETag/304 of the feed ICS (see "ICS Feed Endpoint"). Never a counter and never read-modify-write: `App\Service\CalendarVersionBumper` overwrites it blindly (`UPDATE calendar SET content_version = :uuid WHERE id IN (...)` or `WHERE club_id IN (...)`). `App\Doctrine\ContentVersionListener` collects the affected calendars in `onFlush` (inserts/updates/deletes; an event move bumps old and new calendar; target group/location updates and deletions and a club time zone change bump the whole club; new property/feature/target group/location rows are skipped) and runs the UPDATE in `postFlush`, i.e. after Doctrine's commit (or inside an outer `wrapInTransaction`, rolling back with it): a reader that takes the token before the content can never pair a new token with old content. DB-side `ON DELETE CASCADE/SET NULL` is covered because the parent's deletion is seen. Statements that bypass the unit of work (DQL/SQL `DELETE`/`UPDATE`) must call the bumper explicitly: today `EventService::bulk`, `EventService::deleteEvent` (scope `all`), `EventSeriesService` (rule change deleting events), `HolidayCalendarService::fetchAndStore`. Rule: every new bulk statement on tables that feed the ICS/web output calls `bumpCalendars()`/`bumpClub()` itself; raw SQL calendar inserts must supply `content_version`. The feed configuration (calendar selection, target groups, visibility, secret) needs no calendar token: it stamps `calendar_feed.updated_at`. The in-memory value of an already loaded `Calendar` is not refreshed by a bump.

## Auth

- OAuth2-compliant: short-lived access token (15 min, memory only, per tab) + refresh token (7 days, sliding, `localStorage` key `refresh_token`, so the session survives new tabs and browser restarts; sign-in is kept, not per-tab). Tabs: refresh is serialised across tabs with the Web Locks API (`cc-refresh`; fallback: per-tab single-flight), the access token is broadcast on `BroadcastChannel` `cc-auth` (never the refresh token; refresh-token changes and logout also travel via the `storage` event), a logout in one tab signs out all tabs. Tab-bound state (SSO `sso_code_verifier`, invitation token, feed proof) stays in `sessionStorage`. Legacy per-tab tokens are moved once and removed (`lib/api.ts`).
- No auth cookies. Frontend owns both tokens. (Only the OAuth flow sets a short-lived HttpOnly `oauth_state_nonce` cookie on the API host to bind `state` to the browser.)
- Refresh: `POST /api/auth/token` (form-encoded: `grant_type=refresh_token&refresh_token=<token>`)
- Password hashing: `App\Entity\User` uses `algorithm: auto` (`security.yaml`; resolves to bcrypt cost 13 on PHP 8.4, argon2id/sodium only if PHP's default changes; old bcrypt hashes, incl. the SHA-512 pre-hash for passwords over 72 bytes, keep verifying); `AuthService::login` rehashes on success when `needsRehash()` (no token version bump). Test env: cheap `auto` (cost 5).
- Keys: RSA keypair in `backend/config/jwt/` (gitignored); `JWT_REFRESH_SECRET` for HMAC refresh tokens
- Access and refresh tokens carry `uid`, `tv` and the consent flag `lc` (see "Legal documents and consent"); the flag is fixed per refresh-token family. Refresh tokens are stored (`refresh_token`, id = `jti`, `family_id` = `fam` per session) and rotated on every use (single-use via a conditional `UPDATE ... rotated_at IS NULL`; `AuthService::refresh`). A session ends at the latest `REFRESH_TOKEN_ABSOLUTE_LIFETIME` (default 30 days) after login; access tokens carry `fam` (the family), and flows that continue a session under a NEW family (`sessions/sign-out-others`, MFA disable, password change, passkey deletion) pass the old family's `family_expires_at` on (`CurrentUserResolver::sessionFamilyExpiresAt()` -> `tokenResponse`), so they never extend it (a token without `fam`, max. 15 min old, starts the full lifetime). Presenting an already rotated token revokes the whole family (401 `invalid_refresh_token`), except within `REFRESH_TOKEN_REUSE_GRACE` seconds (default 10) after the rotation: that retry (lost response, parallel tabs) gets another token of the family without revoking. Trade-off: a thief who replays a token inside that window also gets a token (the victim's next refresh then forks the family; only reuse after the window is detected). Every issuance (login, `one_time_token`, SSO, password change, passkey login/deletion) starts a family via `TokenService::tokenResponse`. Legacy tokens without `jti` (from before the rotation) are accepted exactly once (`NonceStore`, a replay is 401) and replaced by a token of a new family (not tracked by family, so `/logout` with one does nothing; bounded by their own 7-day expiry). Trade-off of the `localStorage` refresh token: it survives closing the browser and is readable by XSS (mitigated by the strict CSP and rotation with reuse detection; HttpOnly-cookie variant: Backlog). Tabs no longer copy a token by duplication; tabs serialise refreshes under the lock. `POST /api/auth/logout` (`{refresh_token}`, always 200) revokes the family, `POST /api/auth/logout-all` (JWT, 204) bumps `tokenVersion` and revokes all families; the token version (`tv`, checked on access tokens and on refresh) also ends on password change/reset, e-mail change, passkey deletion and SSO takeover

- Console: `app:secrets:rotate` (see "Secrets at rest"), `app:club:create` (see above), `app:user:create` (`--name --email --password|--password-stdin --language`, interactive, verified address, no consent; for the first user when `RESTRICT_REGISTRATION=true`), `app:user:set-password` (`<id|email> --password|--password-stdin`, ends all sessions, voids reset links and waiting e-mail changes, no mail), `app:user:verify` `<id|email>` (alias `app:user:activate`, marks verified, removes pending codes), `app:user:reset-link <email>` (prints the URL only), `app:user:disable-mfa <id|email>` (operator recovery: turns MFA off, removes TOTP and backup codes, ends all sessions and connected apps, mails the user, no password), cron `app:prune-password-resets`, `app:prune-unverified-users`, `app:prune-refresh-tokens`, `app:prune-security-events` (security log older than one year), `app:geoip:update` (weekly; no-op without `MAXMIND_LICENSE_KEY`), `app:legal:sync` (legal documents), `app:prune-club-invitations` (accepted/declined invitations answered, and open ones expired, more than 30 days ago), `app:prune-oauth` (cron: expired OAuth requests/codes/tokens, ended grants, unused clients)

## Feed self-join and feed access

Club setting `club.feed_signup` (`App\Enum\FeedSignup`: `off` | `internal` default | `public`, column string, migration backfills `internal`; admin-editable via `PATCH /api/clubs/:id` `feedSignup`, returned in club responses for staff only): whether a signed-in NON-member who opens a feed becomes a club member (role `member`) through it: `internal` = `CLUB` and `PRIVATE` feeds, `public` = `PUBLIC` too, `off` = never. It gates only NEW membership; existing members always may claim. `FeedMember` (table `feed_member`, UUID v7, unique (feed,user), `source` assigned|claimed, `createdBy` SET NULL, `createdAt`; CASCADE on feed and user; not audited itself, an added/removed row stamps the feed like other association entities via `UpdateAuditListener`, so a claim changes the feed's ICS ETag) is the access of a non-staff member to a `PRIVATE` feed. `App\Service\FeedAccessPolicy` is the one access rule: a user may include feed F in their personal account iff club member AND (F is PUBLIC/CLUB, or F is PRIVATE and (staff, i.e. viewer+, or a `feed_member` row)); `accessibleFeeds(user, club)` is the batched variant. Claim: `POST /api/feed/:feedId/claim` `{secret?}` (`FeedClaimService`; JWT, verified address and consent required: `/api/feed/:id/(claim|membership)` is excluded from the `public_feed` firewall, `access_control` public rule, `EmailVerificationGateListener`, `ConsentGateListener` and `AccessControlCoverageTest::PUBLIC_PATTERNS`; plain members may call it). Lookup via `PublicFeedService::findJoinableFeed` (same checks as `loadFeed`, but unknown id, wrong/missing secret of a PRIVATE feed and all-archived are one 404 `feed_not_found`); under the club row lock: join (403 `member_signup_disabled` if the setting forbids it, quotas `membersPerClub`/`clubsPerUser`), PRIVATE + non-staff: `claimed` row (idempotent, never downgrades `assigned`; quota `feedMembersPerFeed` 5000); answer `{clubId, clubName, feedId, joined}`. 20/h per user, 60/h per IP (`AuthRateLimiter::assertFeedClaimAllowed`). `GET /api/feed/:feedId/membership[?secret=]` answers `{clubId (only for members, else null), clubName, isClubMember, hasFeedAccess, canJoin, canClaim}` (PRIVATE needs the secret, else the same 404). Staff management (editor+; `FeedMemberService`): `GET /api/clubs/:id/feeds/:feedId/members?page&perPage&q&source` (`X-Total-Count`), `POST …/members {userIds ≤500}` and `POST …/members/by-email {emails ≤500}` -> `{added[, unknown]}` (club members only, PRIVATE feeds only else 422 `invalid_request`, source `assigned`, upgrades `claimed`; the club row lock serialises them with claims), `DELETE …/members/:userId`, `POST …/members/bulk-delete`. Feed responses carry `assignedCount` (one grouped query, `UsageCounts::membersByFeed`). `POST …/regenerate-secret` takes optional `{revokeClaimed}` (deletes the `claimed` rows; the old secret dies either way). `ClubService::removeMember` (leave and removal) deletes the person's `feed_member` rows of that club; user deletion cascades; a visibility change away from PRIVATE keeps the rows.

**Personal subscription ("Mein Abo").** `MemberSubscription` (table `member_subscription`, UUID v7, audited; unique (club,user); CASCADE on club and user) is the personal selection of one club member (any role incl. `member` and admin): `secret` (random 256-bit hex, stored ENCRYPTED like a feed secret, see "Secrets at rest"; the entity returns plaintext because the UI shows the address; always compare with `hash_equals`), join entities `MemberSubscriptionFeed` / `MemberSubscriptionTargetGroup` (composite ids, CASCADE; a row stamps the subscription via `UpdateAuditListener`); empty target group selection = all groups. `App\Service\MemberSubscriptionService`: created lazily and race-safely (`INSERT IGNORE` on the unique key, then a `FOR UPDATE` read, so every change runs under the subscription row lock), by `GET /api/clubs/:id/my-subscription` (no feeds selected) and by `FeedClaimService` (inside the claim transaction: a new subscription has the claimed feed selected and all groups, an existing one gets the feed added). Routes (`MemberSubscriptionController`, voter `CLUB_ANY_MEMBER`, in the `MemberRoleTest` allow-list; own data only): `GET|PUT /api/clubs/:id/my-subscription` (`{id, secret, selectedFeedIds, targetGroupIds, updatedAt}`; PUT is replace with `{feedIds, targetGroupIds}`, both required, <= 500 ids, feeds must be accessible per `FeedAccessPolicy` and have a non-archived calendar, groups of the club, else 422 `unknown_reference`), `POST …/my-subscription/rotate-secret` (old secret dead at once; 10/h per user, `AuthRateLimiter::assertSubscriptionRotateAllowed`), `GET /api/clubs/:id/my-feeds` (`{feeds: [{id, name, visibility, calendarNames, accessReason club|public|staff|assigned|claimed, selected}], targetGroups: [{id, name}]}`; no feed secrets, does not create the subscription, query count independent of the feed count). Selected feeds that are no longer accessible are ignored on read and dropped by the next PUT. `ClubService::removeMember` (leave and removal) deletes the subscription of that club; a role change keeps it; user deletion cascades. **Serving it** (`App\Service\PersonalFeedService`, `PersonalSelection`, `PersonalIcsPlan`): public ICS `GET /api/feed/me/:subscriptionId/ics?secret=` (`PersonalFeedController`, inside the existing `public_feed` firewall and `/api/feed/` public allow-list, route priority above `/{feedId}/...`; unknown id, wrong/missing secret (checked with `hash_equals` right after the first row lookup) and a gone member are one identical 404; rate limits via `assertFeedAllowed` with the subscription id as key, so `FEED_RATE_LIMIT_PER_IP` is shared with the feed routes). Content = published events of the EFFECTIVE feeds: selected AND accessible NOW (same rule as `FeedAccessPolicy`, evaluated in SQL on every request: staff, non-PRIVATE or a `feed_member` row) AND with an active calendar; per feed the filter is the feed's own target groups cut with the subscription's (`PersonalSelection::effectiveGroups`; none = no filter; events without groups drop out of a filtered feed, as everywhere), united into ONE event query (`OR` branch per distinct filter, so an event is never duplicated) and streamed through `IcsEventReader`/`IcsService::streamFeedIcsForZone` (no entities; window, cap, zone as the feed ICS; `X-WR-CALNAME` = `<club> – Mein Abo`, only here, so the golden stays; zero effective feeds = valid empty calendar). The 304 path runs three light queries (subscription+club+role, selected accessible feeds, one UNION of calendar versions / feed groups / subscription groups); ETag = hash of subscription id and `updated_at`, config fingerprint (secret and groups hashed), club name and zone, per effective feed (id, `updated_at`, config fingerprint, effective groups), calendar content versions, window, cap, `FORMAT_VERSION`; `Cache-Control: no-cache, private`; `X-Robots-Tag: noindex` and `Referrer-Policy: no-referrer` from `FeedResponseHeadersListener` (also 304). Calendar view for the SPA: `GET /api/clubs/:id/my-events[?from&to&targetGroupIds[]]` and `…/my-events/:eventId` (any member role, own data; payload like the public feed web view via `PublicFeedService`'s serializers; default groups = the subscription's, an explicit list incl. empty = all overrides; no subscription yet = empty result, nothing is created).

## Secrets at rest

`calendar_feed.shared_secret`, `member_subscription.secret` and `user_totp.secret` (TOTP seed) are encrypted in the database (`App\Security\Secret\SecretCipher`, ext-sodium XChaCha20-Poly1305, random 24-byte nonce). Key = HKDF-SHA256 of `APP_SECRET` with a fixed context label (never the raw secret); associated data = the column purpose (`SecretCipher::PURPOSE_FEED` / `PURPOSE_SUBSCRIPTION` / `PURPOSE_TOTP`), so a value copied into another column fails authentication. Format `enc:v1:<keyId>:<base64url(nonce|ciphertext)>`, `keyId` = fingerprint of the derived key. Key ring: current key from `APP_SECRET` plus the comma-separated older values of `APP_SECRET_PREVIOUS` (env default in `services.yaml`); decrypt picks the key by `keyId`, an unknown one or a tampered value throws `SecretCipherException` (never a silent null, never the value in the message). A value without the `enc:` prefix is legacy plaintext: read as is, encrypted on the next write. Doctrine: DBAL types `encrypted_feed_secret` / `encrypted_subscription_secret` / `encrypted_totp_secret` (`App\Doctrine\Type\EncryptedSecretType`, subclass per purpose, registered in `doctrine.yaml`; types are static, so `Kernel::boot()` hands them a lazy provider of the public `SecretCipher` service); entities keep plaintext getters/setters and dirty-checking compares plaintext (an unchanged secret is never rewritten). Consequences: nothing can query BY a secret in SQL (lookups are by id; verified), and RAW SQL must handle ciphertext itself: `PersonalFeedService` decrypts `shared_secret`/`secret` from its light queries, `MemberSubscriptionService::ensure` encrypts the `INSERT IGNORE` value; tests that seed legacy plaintext by raw SQL stay valid. The ETag inputs use the plaintext secret (hashed), so they do not change on re-encryption. `member_subscription.secret` is VARCHAR(255). New encrypted column: add a DBAL type subclass with its purpose, register it in `doctrine.yaml` and in `App\Security\Secret\EncryptedColumns` (a test fails if a mapped `encrypted_*` field is missing there). `app:secrets:rotate` (`SecretRotator`, `--dry-run`) re-encrypts every registered column under the current key in batches of raw SQL in transactions (no entities, no `updated_at`/content version change, optimistic `WHERE col = old`), is idempotent, prints counts per column and exits non-zero with the row ids (never values) when a row cannot be decrypted; `docker/entrypoint.sh` runs it after the migrations (non-fatal), so upgrades encrypt legacy plaintext. APP_SECRET rotation: set `JWT_PASSPHRASE` to the old value (the JWT key passphrase defaults to APP_SECRET), `APP_SECRET_PREVIOUS=<old>`, new `APP_SECRET`, run the command, remove `APP_SECRET_PREVIOUS`. Other APP_SECRET users (all lost/invalidated on change, none stored): `SignedTokenService` (SSO state, link ticket/proof, passkey challenges, SSO one-time login codes), peppered e-mail confirmation codes (`EmailVerificationService`), stateless reauthentication codes (`ReauthenticationService`: account deletion, passkey registration), the lexik JWT passphrase default and `framework.secret`. Not APP_SECRET: password reset and e-mail change tokens (hashed in the DB), refresh tokens (`JWT_REFRESH_SECRET`), MCP/OAuth tokens (hashed). Operator text: `docs/admin/docs/operations.md`.

## Club invitations

Nobody is added to a club without consent (audit M8; the old `POST /api/clubs/{id}/members` is gone, `GET` list and `DELETE /members/{userId}` stay). Only admins may manage invitations. With `RESTRICT_REGISTRATION` enabled, an open club invitation is the only way to sign up. `App\Service\ClubInvitationService`, entity `ClubInvitation` (table `club_invitation`, UUID v7; normalized lower-case address, `invitedBy` (SET NULL on account deletion), `role` member|viewer|editor|admin (default editor), `status` pending|accepted|declined, `createdAt`, `expiresAt` = +7 days, `resolvedAt`; only the SHA-256 hash of the random token is stored like `password_reset`), mail `club_invitation.mjml` (club name + inviter name only, link `{FRONTEND_URL}/invitations?token=…` and a `/signup` hint, sent after the response via `DeferredMailer`; identical for registered and unregistered addresses).

```
POST   /api/clubs/:id/invitations {email, role?}    # 204 for EVERY well-formed address (unknown, registered, member, already invited): no enumeration; role defaults to editor
GET    /api/clubs/:id/invitations                   # pending + expired (computed `status`), accepted/declined are not listed; includes role
POST   /api/clubs/:id/invitations/:invId/resend     # pending or expired: new token (old link dies), +7 days, new mail; 204; 60 s cooldown per invitation (429 rate_limited)
DELETE /api/clubs/:id/invitations/:invId            # revoke pending/expired; 200 {ok: true}
GET    /api/invitations                             # own open, non-expired ones by VERIFIED e-mail: [{id, clubName, invitedByName, expiresAt, role}]
POST   /api/invitations/:id/accept | /decline       # by id from the list; accept -> 200 {id, name, timezone} of the club, decline -> 204
POST   /api/invitations/accept | /decline {token}   # by the token of the mail link (SPA calls it after sign-in)
POST   /api/invitations/preview {token}             # PUBLIC (no sign-in): 200 {email, clubName, invitedByName, expiresAt} of a pending, non-expired invitation; unknown/answered/expired: same 404 invitation_not_found; 30/15 min per IP (429 rate_limited)
```

Rules: an existing member's address is ignored silently (nothing stored, no mail); an open invitation for club+address is kept (idempotent, no second mail), an expired one is renewed like a re-send. The token only identifies an invitation: the signed-in user's VERIFIED address must equal the invited one, every other case (wrong token/id, other user, unverified user, answered) is the same 404 `invitation_not_found`; an own but expired one is 422 `invitation_expired`. Accepting runs in a transaction under the club row lock (`removeMember` style), respects `membersPerClub` and, for staff roles, `staffPerClub` and does not duplicate an existing membership. Nothing is auto-accepted: after registration/SSO the invitee finds invitations via `GET /api/invitations`. Limits: 20 invitations/re-sends per user and 50 per club and day (`AuthRateLimiter::assertInvitationAllowed`, 429 `rate_limited`), at most 5 invitation mails per address and day (silently no mail, same answer), `Quota::PENDING_INVITATIONS_PER_CLUB` = 200 open invitations (422 `quota_exceeded`). Users without any club are fully supported. Details: `docs/api/openapi.yaml`.

## Legal documents and consent

Imprint, privacy policy and terms of use are operator-provided Markdown files `imprint.md`, `privacy.md`, `terms.md` in `backend/legal/` (env `LEGAL_DOCUMENTS_PATH`, default `%kernel.project_dir%/legal`; real `*.md` are gitignored/dockerignored, `*.md.example` and `README.md` are shipped; the container expects a mount at `/data/legal`, `LEGAL_DOCUMENTS_PATH` in the Dockerfile). `App\Service\LegalDocumentService` syncs them into `legal_document` (UUID v7): on cache clear/warmup (`LegalDocumentCacheWarmer`) and with `app:legal:sync` (called by `docker/entrypoint.sh`, non-fatal, missing documents are logged as warnings). A version is identified by its content hash: changed content = new document row with a new UUID, the old one stays for the consent history; a type whose file is missing is retired. Rendered HTML is produced by the backend. External links instead of files: env `LEGAL_IMPRINT_URL|LEGAL_PRIVACY_URL|LEGAL_TERMS_URL` (absolute http(s) URL, `app.legal_*` parameters); precedence per type is file, then link, then nothing; invalid values are ignored with a warning (`LegalDocumentService::invalidLinks()`, shown by `app:legal:sync` and logged on warmup). A link version is a `legal_document` row with `url` set, empty markdown/html, null title and a constant content hash: a changed URL updates `url` in place (sync status `updated`, same id, so consent is collected once and not again), file-to-link and link-to-file switches create a new version. The API adds `url` (summary, full, `pendingConsents`) and `documentUrl` (consent history); `html` is "" for links. `LegalDocumentService::publicLinks(): array<string,string>` (type => `{FRONTEND_URL}/{type}` or the link, provided types only) is for mails.

```
GET  /api/legal                         # overview of the current documents per type (public)
GET  /api/legal/:type                   # current document (imprint|privacy|terms), 404 legal_document_not_found
GET  /api/legal/documents/:id           # one specific (older) version
GET  /api/auth/consents                 # own consent history (with IP and user agent)
POST /api/auth/consents {documentIds}   # consent to the current documents (old versions: 422 consent_outdated)
```

`POST /api/auth/register` takes `acceptedDocuments` (ids of the current privacy + terms documents; stale/other: 422 `consent_outdated`). Consent gate (`ConsentGateListener`): a signed-in user without consent to the current privacy/terms gets 403 `consent_required` (+ `documents`) on every `/api/*` route except an allow-list (`GET|DELETE /auth/me`, `/auth/consents`, logout, token, providers, delete-account code, health, `/api/legal*`, `/api/feed/*`); without any provided consent document nobody is gated. The gate applies only to sessions that started without up-to-date consents: `TokenService::tokenResponse` stores the claim `lc` (no pending document) in the access and refresh tokens when a NEW session (family) starts (login, SSO/e-mail code, passkey, legacy refresh token, password reset); rotation (`AuthService::refresh`) and in-session re-issuance (`changePassword`, `deletePasskey`, via `CurrentUserResolver::sessionConsentOk()`) carry it over, so a document update never locks out running sessions (it reaches everyone at the next login, at most 30 days); `SessionConsentListener` puts the access-token claim on the security token; with `lc` the gate costs no query, without it the DB check applies (a consent lets the session pass). `GET|PATCH /api/auth/me` and `POST /auth/consents` return `pendingConsents` (all open documents) and `consentRequired` (true only if THIS session is gated; same builder `AuthService::getMe`). Frontend: `lib/legal`, `components/legal/` (`LegalLinks` in the footer of `AuthLayout` and `PublicShell` (an externally linked document, `url` set, is a plain `<a>`; `/imprint` etc. redirect to it with `window.location.replace`; in signup, consent gate/banner and consent history it opens in a new tab), `LegalDocumentView`, `ConsentCheckboxes`), `/imprint` `/privacy` `/terms` as routed modal (with background state) or standalone `LegalPage`, consent checkboxes in the signup form, `ConsentPage` as gate in `ProtectedRoute` (besides accepting and signing out it offers the consent history in a modal and account deletion via `DeleteAccountDialog`), `LegalSection` (consent history) in the profile. While a session runs, a document update only shows the dismissible `ConsentChangeBanner` (`pendingConsents` without `consentRequired`; `ProtectedRoute` places it, the dialog accepts via `POST /api/auth/consents`); the gate follows at the next sign-in. E-mails: the footer of every mail (`footer.mjml`) shows the links via the Twig function `legal_links()` (`App\Twig\LegalLinksExtension` → `LegalDocumentService::publicLinks()`, labels `email.footer.*`; no link line when none exists). Details: `docs/api/openapi.yaml`, `backend/legal/README.md`.

## MCP server and OAuth

Remote MCP server (Streamable HTTP) at `/api/mcp` plus an own OAuth 2.1 authorization server, so AI clients can read the calendar and draft events for a signed-in user. Reference of every route, error code and the tool catalogue: `docs/api/openapi.yaml` ("MCP server and OAuth"). Frontend: consent page `/oauth/consent` and profile section "Verbundene Apps" (`frontend/AGENTS.md`).

- **Code:** `App\OAuth\` (controllers with attribute routes, `OAuthServerService`: PKCE S256, codes, tokens, rotation; `RedirectUriPolicy`; `OAuthConsentService`), `App\Mcp\` (`McpContext`, `Security\McpAuthenticator`, tools in `Mcp\Tool\` as `#[McpTool]` services), config `config/packages/mcp.yaml` (path `/api/mcp`, session store `cache`, `allowed_hosts` from the trusted hosts in `services.yaml`). Entities (UUID v7, one migration): `OAuthClient`, `OAuthAuthorizationRequest` (10 min), `OAuthAuthorizationCode` (60 s, single use, reuse revokes the grant), `McpGrant` (id = family, `revokedAt`), `McpToken` (access|refresh, `tokenHash` unique).
- **Browser binding:** `GET /api/oauth/authorize` generates a random nonce, sets it as cookie `oauth_consent_<requestId>` (HttpOnly, SameSite=Lax, path `/api/oauth`, Secure per request scheme, lifetime = request TTL; one cookie per request so parallel flows in one browser do not collide) and stores only its SHA-256 on `OAuthAuthorizationRequest.browserBindingHash`. `OAuthConsentService::openRequest` (describe and decision, before any state change) requires the cookie via `hash_equals`; missing/wrong cookie, legacy rows with a null hash, unknown and expired all give the same 404 `authorization_request_not_found` and never delete the request; a successful decision clears the cookie. The cookie survives sign-in, SSO and passkey detours (same browser, 10 min). A split setup (`VITE_API_URL` on another origin) works only when both origins are the same site: `nelmio_cors` allows credentials for the exact `FRONTEND_URL` on `^/api/oauth/(authorization-request/|authorize/decision$)` only, and the SPA sends `credentials: include` for `/api/oauth/*` (`apiFetch`).
- **Discovery:** `/.well-known/oauth-authorization-server` (RFC 8414) and `/.well-known/oauth-protected-resource[/api/mcp]` (RFC 9728) are NOT under `/api`: `.htaccess` and `docker/Caddyfile` route them (and `/api/mcp`, with `flush_interval -1` in Caddy) to Symfony; a custom web server must do the same, else MCP clients cannot discover the server. URLs come from `APP_URL`/`BACKEND_URL`, never the request.
- **Auth:** firewall `mcp` (`^/api/mcp`, before `api`) with the stateless `McpAuthenticator`; the `jwt` firewall never accepts MCP tokens and vice versa. 401 carries `WWW-Authenticate: Bearer resource_metadata=…`; `OPTIONS` passes unauthenticated. After the token: current legal consent (`consent_required`) and verified e-mail are required (same as the consent step). Public clients only (no secret), authorization code + PKCE S256 only, `resource` bound to `APP_URL/api/mcp`, dynamic registration (RFC 7591), revocation (RFC 7009).
- **Tokens:** opaque 256-bit random, only the SHA-256 hash is stored. Refresh tokens rotate with reuse detection and grace like `AuthService::refresh`. Env (defaults in `services.yaml`, documented in `.env.example`): `MCP_ACCESS_TOKEN_TTL` (3600), `MCP_REFRESH_TOKEN_LIFETIME` (604800), `MCP_REFRESH_TOKEN_ABSOLUTE_LIFETIME` (2592000), `MCP_REFRESH_TOKEN_REUSE_GRACE` (10), `MCP_ALLOWED_CLIENTS` (default `claude,openai,gemini`; empty string = all clients, also loopback; unknown entries fail at boot).
- **Scopes:** `mcp:read`, `mcp:write` (implies read), no per-club restriction. The scope is only the ceiling: every tool calls `McpContext::requireScope()` and `requireRole()` against the user's CURRENT `ClubUser` role, never a role cached in the token.
- **Allowed clients** (`RedirectUriPolicy`, matched on redirect URI, loopback ports ignored): `claude` (`https://claude.ai/api/mcp/auth_callback`, loopback `/callback`), `openai` (`https://chatgpt.com/connector_platform_oauth_redirect`, `…/connector/oauth/<id>`), `gemini` (loopback `/oauth/callback`). Always: https or http on loopback, no fragment/userinfo/wildcard. `MCP_ALLOWED_CLIENTS`: family list; `*` alone = every client (`OAuthClient.family` null, "unverified app"); empty = no client; `*` mixed with others or unknown entries fail at boot. `RedirectUriPolicy::permits` re-checks a stored client against the CURRENT list at `GET /api/oauth/authorize` (a null-family client needs `*`; existing grants/tokens are not affected). The self-declared `client_name` is only a claim: the consent API and the grants list return `label` (derived from the family: Claude/ChatGPT/Gemini, `RedirectUriPolicy::label`) and `claimedName`; the UI shows the label as identity, the claim as "calls itself ..." only when it differs, and warns for `callbackRisk` (`loopback`, `chatgpt.com/connector/oauth/<id>`, which a third party can own: a family match proves only the callback's shape).
- **Tools** (exact list asserted by a test; all descriptions say returned content is untrusted data). Read (`mcp:read`): `list_clubs`, `list_calendars`, `list_events`, `get_event`, `list_target_groups`, `list_properties`, `list_features`, `list_locations`, `list_event_templates`, `get_event_template`, `list_feeds`, `get_feed` (feeds: editor, WITH shared secret; drafts only for editors). Write (`mcp:write`, editor unless noted): `create_event_draft` (always a draft), `update_event_draft` (only still-draft events, row lock, `event_not_draft`), `create_target_group`, `create_property`, `create_feature`, `create_location`, `create_event_template`, `update_event_template`, `delete_event_template`, `create_feed` (admin; `CLUB` or `PRIVATE` only). Deliberately NOT exposed: deleting/publishing events, series, import, bulk, updating/deleting target groups/properties/features/locations, feed update/delete, public feeds, members, invitations, accounts. Tools reuse the existing services and map `ApiProblemException` to `ToolCallException` (code + detail). New tool = new test case in the tool list test + `docs/api/openapi.yaml`.
- **Grants:** users list/revoke them at `GET /api/auth/mcp-grants`, `DELETE /api/auth/mcp-grants/{id}`. `RevokeMcpGrantsOnSessionEnd` (Doctrine entity listener on `User`) revokes all grants on every `tokenVersion` bump (sign out everywhere, password change/reset, e-mail change, passkey deletion, SSO takeover); account deletion cascades.
- **Limits:** `/api/mcp` 120/min per grant and per IP, registration 10/h per IP, `/api/oauth/token` and `/api/oauth/revoke` 60/min per IP together (429 `rate_limited` + `Retry-After`, checked before any DB work), consent decisions 30/h per user (`AuthRateLimiter`), `Quota::MCP_CLIENTS_PER_USER` 20 grants per user. Cron: `app:prune-oauth`.
- **CORS:** `nelmio_cors` allows only `FRONTEND_URL`; browser-based MCP clients on another origin do not work (server-side connectors and CLIs do). Token responses are `Cache-Control: no-store` (`OAuthResponse`).

## API Errors

Every error is an RFC 7807 body (`App\Http\ProblemResponse`) with a stable `code` (and `field` for input errors) via `App\Exception\ApiProblemException`, e.g. `validation_failed`, `invalid_request`, `unknown_reference`, `duplicate_name`, `too_many_events`, `quota_exceeded`, `email_taken`, `registration_restricted` (403, field `email`), `club_creation_restricted` (403), `invalid_credentials`, `email_not_verified` (login 403), `invalid_refresh_token`, `invalid_passkey`, `member_not_found`, `invitation_not_found`, `invitation_expired`, `ics_fetch_failed`, `rate_limited`, `forbidden`, `invalid_role`, `last_admin`, `consent_required` (403, `documents`), `consent_outdated` (422, `documents`), `legal_document_not_found` (404). A 401 of the access token is always `missing_token` / `invalid_token` / `token_expired` (`App\Security\JwtProblemListener`; also replaces the JWT bundle's bodies; the sign-in routes answer 401 `invalid_credentials` / `invalid_refresh_token` / `invalid_passkey`), every 401 with `WWW-Authenticate: Bearer`; club, calendar and geocoding routes answer 401 without a token before any id is looked up (`access_control`), 403 only to signed-in non-members. Status rule: malformed input (typed `Input` checks, incl. time zones and coordinates) is 400, DTO constraint violations and state conflicts 422; every 400 has a code (framework 400s `invalid_request`, array query parameters `validation_failed` + `field`). The frontend matches `ApiError.code`, never `detail`. Full list: `ErrorCode` in `docs/api/openapi.yaml`.

## Limits and Quotas (audit M7)

All quotas live in `App\Service\Quota` (`LIMITS`, generous on purpose; checked by a count before the write via `Quota::assertRoom()`); exceeding one is 422 `quota_exceeded` with the members `resource` and `limit`: 50 clubs per user, 100 calendars per club (create + duplicate), 5000 members per club in total and 500 staff (viewer/editor/admin, `staffPerClub`, also checked when a `member` is promoted) per club, 20000 events per calendar (create, from-template, series create/rule change, import), 2000 locations per club (import included), 500 target groups per club, 50 feeds per club, 500 each of properties/features per calendar, 20 holiday calendars per calendar, 20 MCP grants (`mcpClientsPerUser`) per user. Per-request caps: 5000 events/locations per import and 5000 ids per bulk (413), 366 events per series and 366 `dates` of `from-template` (422 `too_many_events`), 500 distinct ids per id-list field (`Input::MAX_IDS`, 400), holiday ICS 1 MB / 5000 events (`HolidayCalendarService`). `GET …/events`: at most 1830 days between `from` and `to` (400 on `to`), `limit` (default and max 5000) and `offset`, `X-Total-Count` header, body stays a plain list (the list page without `from`/`to` shows at most the first 5000). A new create route must call `Quota::assertRoom()`; document it in `docs/api/openapi.yaml` ("Quotas and input limits"). The frontend shows one toast for every `quota_exceeded` (`errorFrom` in `frontend/src/lib/api.ts`, `common.quotaExceeded`).

## End-user documentation (/help)

In-app help for club members, public at `/help` and `/help/*` (SPA routes; the existing `/help/subscribe` route takes precedence, so no page may use the slug `subscribe`). Content: Markdown in `frontend/docs/{de,en}/**/*.md` with frontmatter `title`, `order`, `description`; slug = path without `.md` (`index` = `/help`, `<folder>/index` = `/help/<folder>`; `docPath` strips the `/index`), section = first folder, whose two-digit prefix (`10-name/`) orders the sections and is stripped from slugs/URLs (unprefixed sections last); a folder URL without an index page shows a generated table of contents of its pages and child folders (`resolveHelpPath` in `src/docs/nav.ts`, which HelpPage uses on the pathname, not `useParams`: the outer splat route leaks `*`), an unknown folder is the not-found state; every page must exist in BOTH languages. Compiled at build time by the Vite plugin (`frontend/vite/docs-plugin.ts`, `docs-compiler.ts`): one hast JSON module per page (lazy chunk) and one MiniSearch index per language, no Markdown parser at runtime, raw HTML in Markdown is dropped. Syntax beyond Markdown: `![alt](shot:<id>)` (screenshot `frontend/docs/screenshots/<lang>/<id>.png`; the build fails when it is missing), `[text](help:<slug>#anchor)` (internal link, the build fails on unknown slugs), `:::note|tip|warning` ... `:::` callouts, `:::tabs [key=<param>] [platform]` with `:::tab <id> <label>` ... `:::` blocks and a closing `:::` (accessible tabs, active tab in the `?<key>=` query param). `frontend/src/docs/slugs.generated.ts` (typed `DocSlug`) is committed and rewritten on build/dev (a Vitest test catches drift). From screens link with `<HelpLink page="..." anchor?>` or `useHelpUrl`/`helpPath` (`src/docs/paths.ts`), a wrong slug is a compile error; the footers of `AuthLayout` and `PublicShell` show exactly one help link (`HelpCenterLink`: the help page of the current screen via `src/docs/contextHelp.ts`, `/help` as fallback, on the public feed page straight to `/help/publishing/subscribe` via `PublicShell`'s `helpLink` prop); every help link (sidebar, footers, MorePage) opens in a new tab, the help pages show only the legal links in their footer, and the sidebar and `MorePage` use the same context-sensitive link. Screenshots are generated by the Playwright project `docs` (`frontend/e2e/docs/*.docs.ts`, `npm run docs:screenshots`; needs the E2E environment from `docs/ops/E2E.md`; PNGs are committed). Contributor workflow: `frontend/AGENTS.md`.

## Event Import, Export, Bulk, Series

```
POST /api/calendars/:id/events/import/preview   # {events, locations?} → status per entry (new|duplicate|invalid), writes nothing; new locations reference club-scoped locations
POST /api/calendars/:id/events/import           # {events, locations?: [{tempId, name, …}], skipDuplicates?} → one transaction; locations scoped to club
GET  /api/calendars/:id/events.ics?from&to&includeDrafts&targetGroupIds[]   # member ICS download (target groups club-scoped)
POST /api/calendars/:id/events/bulk             # {ids, action: publish|draft|delete} → {affected}, all or nothing
POST /api/calendars/:id/events/series/preview   # {rule} → {dates, count, skippedHolidays, holidays}, writes nothing
POST /api/calendars/:id/events/series           # {rule, templateId?, event?, isDraft?} → {series, events}, atomic, max. 366
GET  /api/calendars/:id/event-series/:seriesId  # rule + eventCount
PATCH|DELETE /api/calendars/:id/events/:eventId # scope this (default) | all (PATCH body, DELETE ?scope=)
```

Duplicates: same `externalUid` (ICS UID, stored on `Event`) or same name + start date. Unknown time zones in the import fall back to the calendar zone with a `warnings` entry. Limits: 5000 events per import/preview and 5000 ids per bulk request (413 `too_many_events`), 366 events per series (422 `too_many_events`). Series dates are computed only by the backend (`App\Service\SeriesRule`); `scope: "all"` never changes an event's date; empty series are removed. Details: `docs/api/openapi.yaml`.

## PDF Export

```
GET /api/calendars/:id/events.pdf?from&to&layout&paper&orientation&includeDrafts&targetGroupIds[]   # member download (viewer+, archived allowed)
```

`layout`: `month-grid`, `quarter-overview` (>= 3 months), `annual-overview` (full calendar year only), `agenda`; `paper` a4|a3, `orientation` auto|portrait|landscape. Same filter as `events.ics` (`EventExportService`). Optional `holidayCalendarIds[]` (max 20, own holiday calendars, else 422 `unknown_reference`; default none) prints holidays in every layout (`PdfHolidaySelection` loads and refreshes, `PdfHolidays` computes the per-day marking): public/other holidays colour the day and print the name, school holidays colour the range and print the name on its first visible day only; colour priority grey out-of-range, public, weekend, school; the quarter layout prints the name only on a day with a free line (never changes the line counts), annual shows colour only; legend entry for the colours used. Caps: 366 days (400 on `to`), 2000 events (422 `too_many_events`, field `to`; `PdfExportService::MAX_*`). Rate limit `AuthRateLimiter::assertPdfExportAllowed`: 10/user and 30/IP per 10 min (`pdf_export_*` in `rate_limiter.yaml`), checked first. Language (`de`/`en`) and first weekday come from the signed-in user's stored preferences, not from parameters. Code: `App\Pdf\` (`PdfExportService` builds the view model and renders Twig `templates/pdf/*.html.twig`; `PdfOptions`, `PdfLayout`, `PdfMonthGrid`/`PdfQuarterOverview`/`PdfAnnualOverview`, `PdfText`, `PdfDates`), route `EventController::exportPdf`, events read through `IcsEventReader`. Hardening (`DompdfFactory`): remote, PHP and JavaScript off, chroot `backend/assets/pdf`, only `file://` allowed, cache in `var/cache/<env>/pdf`; user text is escaped by Twig, emoji are stripped from names. Property icons are shown only as PNGs from the allow-list `backend/assets/pdf/emoji/` (Noto Emoji, Apache-2.0, `manifest.json`, resolved by `EmojiImages` through a strict key regex, never a path from input; unknown icons omitted) and explained in a legend of the used properties. The route raises `memory_limit` to 512M and the time limit to 60 s and restores them afterwards; the response is built in memory (`Content-Length`, `Cache-Control: no-store`). Quarter layout (`PdfQuarterOverview`): one page per three touched months, one column per month with one row per day (grey filler rows up to 31, grey out-of-range days, weekends tinted, min. 2 lines per day) and one nowrap line per event (`time emoji title (features)`, `features` key of the per-day entries); the font size scales per page from the fullest month (4.5-8 pt, overflow to a second page below the minimum); lines are cut by an estimated text width (`PdfEventLine::text`, shared with the month grid) because dompdf wraps lines with inline images despite `white-space: nowrap`; month grid (`PdfMonthGrid`): events use the same line format (`time emoji title (features)`, drafts orange italic without a label), cut to the cell width computed from `PdfOptions::contentWidthPt()`, cell cap and `+N weitere` unchanged; header on every page (base block `header` is empty), the emoji legend is per page (`legend` of each page, the global one stays empty). Shared CI styling (brand `#0b6b58`, brand-soft `#dcefe9`, border `#cfd7d2`, ink `#14221e`, muted `#4a5b55`, filler grey `#e6e6e6`, drafts `#b45309` italic) is defined once in `base.html.twig`: month headings are full-width brand bars (`div.bar`), Saturday/Sunday are tinted (`weekend` flag from `PdfDates::isWeekend` on month-grid/annual cells, annual event list and agenda rows), and month grid, annual and agenda get the club/calendar+period header on every page from the base `header` block (a `position: fixed` element in the page margin; the quarter prints its own inline header). Annual days with events are solid brand green. Document metadata: Author is the club name (control characters and emoji removed, max. 200 chars), Creator is `Club Calendar (<APP_URL>)` (`DompdfFactory::creator()`, plain `Club Calendar` when `APP_URL` is not a clean http(s) URL), Producer stays dompdf's; dompdf stores them as UTF-16BE. Details: `docs/api/openapi.yaml`, `docs/admin/docs/hosting-without-docker.md` (PHP limits, proxy timeouts).

## ICS Feed Endpoint

```
GET /api/feed/:feedId/ics
GET /api/feed/:feedId/ics?secret=<token>   # for private feeds
GET /api/feed/:feedId/events[?from=YYYY-MM-DD&to=YYYY-MM-DD]   # web view: header (club, feed name, zone, visibility, eventCount), events and holidays of all selected calendars merged, holidays de-duplicated by uid
GET /api/feed/:feedId/events/:eventId                          # one published event (secret checked first)
GET /api/feed/:feedId/events/:eventId/ics                      # that event as a one-event ICS download ("Add to calendar"); same access rules
```

The one-event ICS (`PublicFeedService::streamFeedEventIcs`) goes through the same `IcsService::streamFeedIcs` with a single chunk, so its VEVENT/VTIMEZONE equals the feed's (no ETag, `no-store`); the frontend has no ICS writer. Feed ICS contains events only (no holidays) and only a default window (env `FEED_ICS_WINDOW_ENABLED` default true, `FEED_ICS_PAST_DAYS` 180, `FEED_ICS_FUTURE_MONTHS` 24, overlap rule, days in the club zone; `FEED_ICS_MAX_EVENTS` default 0 = unlimited, otherwise the first N by date/time as protection, no error; invalid values fail; no query override; member export and web view unaffected).

**ICS event text:** `LOCATION` and the `X-ADDRESS` of `X-APPLE-STRUCTURED-LOCATION` are `Name\nStreet\nZIP City\nCountry` (one part per line like Apple, empty parts skipped, control characters stripped per part; `X-TITLE` is the plain name; `IcsService::buildLocationStr`, `EventFactory`); `SUMMARY` = `<badge emojis joined by space> <name> (<extras, comma-separated>)` (emojis/parentheses omitted when empty); `DESCRIPTION` = note, `Zusatzangebote: …`, `Gruppen: …` and a legend `Besonderheiten:` with one `<emoji> <badge name>` line per used icon (German labels, as before). `IcsEvent::propertyNames` parallels `propertyIcons`.

**Conditional requests (feed ICS only):** `PublicFeedService::prepareFeedIcs` returns a `FeedIcsPlan` with the ETag before any event query; the controller answers `304` on a matching `If-None-Match` and renders (`renderFeedIcs`) only otherwise. Order: rate limit, `loadFeed` (visibility/secret via `hash_equals`, all-archived 404), then ETag compare, so a 304 never exists without access. ETag = strong, first 32 hex chars of sha256 over: feed id, `calendar_feed.updated_at` (DATETIME, SECOND precision), a fingerprint of the feed configuration (name, visibility, hash of the secret input, feed target groups; this closes the two-changes-in-one-second gap of `updated_at`), `id => content_version` of the active selected calendars (one light SQL query, no hydration), the effective target group set (requested ids cut with the feed's own, sorted, de-duplicated by `normalizeTargetGroupIds`), the resolved window (dates or `none`) and `FEED_ICS_MAX_EVENTS`, the club time zone and `IcsService::FORMAT_VERSION`. The secret is never in the ETag value. Headers: `ETag`, `Cache-Control: no-cache, public` (PUBLIC/CLUB) or `no-cache, private` (PRIVATE), no `max-age`; the 304 carries the same headers, `FeedResponseHeadersListener` treats 304 like a success for `X-Robots-Tag`. Rules: **every change of the ICS output (fields, formatting, library upgrade changing the text) must increase `IcsService::FORMAT_VERSION`**; every new input of the ICS output must flow into the ETag. The window start moves with the date, so the ETag changes at midnight in the club zone. A shared cache/CDN in front may store the PUBLIC/CLUB response but must revalidate (`no-cache`); the web view and member export have no ETag. **ICS read path (feed ICS and member export):** no entity hydration; `App\Ics\IcsEventReader` runs the filtered event query (`QueryBuilder` with root alias `e`, sorted date, time_begin, id) as array rows with the calendar zone and location columns joined, plus one query per association (property icons, feature and target group names; batches of 500 events, ordered by assignment id) and returns readonly `IcsEvent`/`IcsLocation` DTOs, which `IcsService` renders (no entity access in the ICS path). **Streaming:** the output is not built as one string. `IcsEventReader::chunks($qb, $limit)` is a generator of event chunks (default 500, constructor arg `chunkSize`) read by keyset pagination over `(date, time_begin, id)`; the `FEED_ICS_MAX_EVENTS` cap is the `$limit` over all chunks (the last chunk is shortened). `IcsService::streamFeedIcs|streamCalendarIcs` yield text pieces: the envelope (rendered by eluceo from an empty `Calendar`, `END:VCALENDAR` cut off), per chunk the VEVENT blocks (eluceo's `EventFactory::createComponent`, so escaping/folding stay the library's), then the VTIMEZONE blocks, then `END:VCALENDAR`. eluceo itself writes events BEFORE the VTIMEZONEs, so no pre-pass is needed: the min/max span per zone (±1 day) is collected while streaming and the VTIMEZONEs follow the last chunk. The controllers return a `StreamedResponse` (`IcsService::outputCallback` echoes and flushes per piece): **no `Content-Length`** (chunked), ETag/Cache-Control/Content-Disposition/`X-Robots-Tag` are set before streaming; access, secret, rate limit, validation and the 304 decision happen before, so those errors stay RFC 7807 responses. A failure while streaming (e.g. DB gone) is logged (`ICS stream aborted`) and ends the output without `END:VCALENDAR` (the status is already sent and cannot change; clients see an invalid file). Memory is independent of the event count (about 3 MB per request in a non-debug kernel; the debug query collector of the dev/test kernel keeps every parameter list). Caddy/`.htaccess` compression (`encode zstd gzip`, mod_deflate) works with the chunked body. Tests read streamed bodies with `$client->getInternalResponse()->getContent()` (`getResponse()->getContent()` is false). `backend/tests/Service/IcsGoldenTest.php` pins the output byte for byte against `tests/Service/fixtures/ics-golden.txt` (`UPDATE_GOLDEN=1` regenerates it: a diff there means `FORMAT_VERSION` must rise); memory check: `phpunit --group performance` (excluded by default). Feed web view merges published events and holiday events of all selected non-archived calendars in the feed's timezone; if all selected calendars are archived, returns 404. Feed management responses (`/api/clubs/:clubId/feeds…`) omit `sharedSecret` unless `?includeSecret=1|true` is sent (the frontend sends it where it shows or copies the feed address). Deleting a calendar deletes feeds whose only calendar it is; other feeds simply lose that calendar from their selection.

Counters for lists and delete dialogs (clubs, calendars, `usage` of reference data, `eventCount` of templates) come
from the API in one grouped query per counter (`App\Service\UsageCounts`); the frontend never loads whole lists just
to count. Details: `docs/api/openapi.yaml`.

## E2E Tests

Playwright (`frontend/e2e/`). The suite registers users and writes data, so it runs **only against an isolated local
environment**: own database `club_calendar_e2e` on the test MySQL (port 3360), backend via `php -S 127.0.0.1:3001`,
Vite on port 5199. `e2e/global-setup.ts` aborts when `PLAYWRIGHT_BASE_URL`, `E2E_API_URL`, `VITE_API_URL` or the API
URL of the running Vite server is not on localhost (`frontend/.env.local` points at the dev API). Step-by-step setup
and cleanup: `docs/ops/E2E.md` (also in `frontend/AGENTS.md`).

```bash
PLAYWRIGHT_BASE_URL=http://localhost:5199 npm run e2e -w frontend   # after the setup from E2E.md
npm run e2e:ui -w frontend                                          # interactive UI mode
```

The E2E backend must run with `MCP_ALLOWED_CLIENTS='*'` (setup command in `docs/ops/E2E.md`) and without legal documents: real `LEGAL_*_URL` values in the shell or `backend/.env.local`, or real files in `backend/legal/`, make registration require consent checkboxes (override the URLs with empty values).

Specs in `frontend/e2e/`: `auth`, `onboarding`, `calendar`, `events`, `series-change`, `templates`, `import`,
`import-rrule`, `import-keyboard`, `import-large`, `error-page`, `dialog-stack`, `settings`, `feeds`, `club`, `profile`,
`public`, `regressions`, `session-revoked`, `stale-assignments`, `account`, `event-template-suggest`, `help`, `mcp-consent`, `csp` (`*.spec.ts`; `csp` only runs with `E2E_CSP=1` against a production build); helpers in `helpers.ts`, guard in `safety.ts` / `global-setup.ts`.

Help screenshots: `frontend/e2e/docs/*.docs.ts` run only in the Playwright project `docs` (`npm run docs:screenshots`), never in the normal `chromium` project; `frontend/e2e/help.spec.ts` covers the help pages.
